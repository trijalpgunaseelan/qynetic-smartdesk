# Security and limitations

This is a development prototype, not production-ready. The HTTP API uses bearer-token authentication over **unencrypted HTTP**. Any device on the hotspot/LAN can potentially observe the token and private reminder data. Use a trusted private hotspot only, do not port-forward, and do not reuse passwords as tokens. Only health and the static dashboard are public. Status, Bluetooth notification contents, pairing codes, and actions require the bearer token. NVS data and Wi-Fi credentials are stored unencrypted. Bluetooth uses authenticated encrypted passkey pairing and persisted bonds. Notifications are held in RAM and cleared when a Bluetooth session ends. Because the dashboard uses plaintext HTTP, its token, notification content, and pairing codes still require a trusted network. Serial UNPAIR explicitly clears bonds; repeated pairing does not silently replace them.

The iPhone hotspot must permit the ESP32 to join; the ESP32 is an ordinary Wi-Fi station. Some iPhone Personal Hotspot configurations may require **Maximize Compatibility**. Keep the hotspot active during initial association; iOS may disconnect idle hotspot clients. iPhone Shortcuts requests to the ESP32 require both devices to be reachable on the same hotspot network; some hotspot networking scenarios restrict local connectivity. Check the assigned ESP32 IP in serial logs or router/hotspot client diagnostics.
